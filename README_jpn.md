## 🎯 概要

**Universal Robot Tool Controller（URTC）** のブラウザベースのコンパニオン
——[Web Serial API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Serial_API)
経由で USB-CAN アダプター越しに実際の URTC ハードウェアと通信することを目指した（実機で動かしたことはありません）
React/Vite シングルページアプリで、2 つのデスクトップコンパニオンツール、
[URTC Flasher](https://github.com/JuanenRac/URTC-FLASHER) と
[URTC Tester](https://github.com/JuanenRac/URTC-TESTER) と同じ SLCAN
フレーミングと CAN プロトコルを使用します。目標は、それら 2 つのツールの主要なワークフローを単一のブラウザタブにまとめることであり、簡略化されたデモではありません。完全な同等性にはまだ達していません（下の「未対応の項目」を参照）——Flasher Studio と Tester Studio タブは、
[URTC ファームウェアリポジトリ](https://github.com/JuanenRac/URTC) の
`docs/CANBUS.TXT` に記載された実際の CAN フレームを送受信します。

### 何が本物で、何がサンドボックスか

本アプリには 2 種類のタブがあります：

- **実際のハードウェア駆動タブ** —— Flasher Studio、Tester Studio、そして
  CAN Bus Protocol Analyzer。これらは、実際の USB-CAN アダプターを接続
  （右上のヘッダーボタン）した時点で初めて何かを行います。送信するすべて
  のコマンドと表示するすべての読み取り値は、CAN バスから来ます（この経路を実際のアダプターやボードで動かしたことはありません）。
  これには実際の**サーマルカメラの読み取り**も含まれます——Tester Studio
  の「Thermal Inspection」パネル（`0x250`/`0x251`/`0x254`/`0x255`）が、
  ツールヘッドの実際の MLX90640 赤外線アレイを CAN 経由で照会します。
- **オフラインサンドボックスタブ** —— Control（ツールカタログ）、OLED、
  Specs/BOM、そして Thermal IR Inspection。これらにより、ハードウェアを
  一切接続することなく、25 種類のツールカタログを探索し、OLED ステータス
  画面をプレビューし、BOM/ピン配置を閲覧し、シミュレートされたサーマル
  カメラフィードを表示できます。ヘッダーの「FW v0.0 / v0.1」トグルは、
  これらのサンドボックスタブ（特定のファームウェアビルドがどのツール
  プロファイルをアンロックするか）にのみ影響し、実際に接続されたボードが
  報告する内容には一切関係ありません。
  - **2 種類のサーマルビューを混同しないでください**：独立した
    「Thermal IR Inspection」タブ（`ThermalCameraViewer.tsx`）は、
    100% クライアントサイドの `Math.random()` ノイズであり、CAN トラフィック
    はまったくありません——これは UI のモックアップであり、センサーの読み
    取り値ではありません。実際の MLX9064x データは、Tester Studio の
    「Thermal Inspection」パネル内にのみ、しかもハードウェアが接続されて
    いる場合にのみ表示されます。

## 🧩 URTC での役割

URTC-WEB-STUDIO は URTC の 2 つのデスクトッププログラム、URTC-FLASHER と URTC-TESTER のブラウザー版です。USB-CAN アダプターと Web Serial で URTC ボードと通信する React のページで、同じ SLCAN のフレーミングと同じ CAN プロトコルを使います（表とベクトルは URTC-COMMON から生成されます）。インストール不要でブラウザーのタブに主な作業を持ち込み、ブラウザーでは扱えない SWD/JTAG はデスクトップのフラッシャーに任せます。25 種のツールをオフラインで調べ、何も送信しないサンドボックスのタブもあります。

## ✨ 機能

### Flasher Studio ——実際の機能カバレッジ

`URTC-FLASHER` 自身の `flasher_protocol.py` から移植され、同じ CAN ID
に対して動作します：

- **メインボードの CAN-OTA 更新**（`0x7F0`-`0x7F7`）：ブートローダー起動
  トリガー、共有鍵の HMAC-SHA256（シミュレーターに対してのみテスト済み）、ページ ACK フロー制御とリトライ/バック
  オフを伴うページ単位の転送、CRC32 + 宣言バージョンの END_UPDATE、
  そして終端状態処理（デスクトップツールと同じ方法で、失われた確認
  フレームからの復旧を含む——誤った失敗を報告するのではなく、バージョン
  を再照会します）。
- **拡張スレーブの CAN-OTA 更新**（`0x210`-`0x219`、メインボード自身の
  I2C ブリッジ経由で中継）——同じ署名/CRC 方式、このパスにはページ ACK
  もハートビートもありません（実際のプロトコルと一致；進捗はプッシュ
  されるのではなくポーリングされます）。
- **ダウングレード認可**（`0x7FD`）——確認ゲート付きのチェックボックス
  で、信頼できる古いリリースへ意図的に戻すために、今回の試行がブート
  ローダーの防ロールバックチェックを回避することを認可します。
- **フラッシュ前の F-RAM 消去**（`0x192`）、任意、メインボードのみ。
- **CAN エラーカウンター照会**（`0x7FB`/`0x7FC`、CAN コントローラー
  自身のエラーレジスタから直接読み取り）——本物のバス問題とアプリケー
  ション/ブートローダー側の問題を区別します。
- **CAN 経由のファームウェア読み戻し/バックアップ**（`0x7FE`/`0x7FF`）
  ——上書きする前に、メインスロットの現在の内容を、ホストの ACK を伴い
  2KB/ページのペースで読み戻し、`.bin` ダウンロードとして保存します。
- **ライブなボードバージョン照会**（`0x7F8`/`0x7F9`/`0x7FA`/`0x7E9`）——シミュ
  レートされたトグルではなく、実際の応答元（アプリまたはブートローダー）、
  HardwareID、バージョンを表示します。
- **公開された署名とダイジェスト**——URTC のビルドが出力する各イメージには
  `<file>.manifest.json`（バージョン、`sha256`、ブートローダーが期待する
  `hmac_sha256` の値。共有鍵の HMAC-SHA256 であり非対称署名ではありません）と `<file>.sha256` が付属します。アプリはその公開署名を
  送信し、マニフェストの `sha256` がファイルと一致しない場合は書き込みを
  **ブロック**し、マニフェストのバージョンをブートローダーに報告します。
  ディスクから選んだファイルにはマニフェストがないため、その 1 回の書き込み
  用に入力した署名鍵でのみ書き込めます（ベンチ用ボード）。ただし、その
  `.manifest.json` を一緒に選んだ場合は除きます。
- **ファームウェアのパッチ番号**（`0x7E9`、およびスレーブの拡張された `0x218`）
  ——インストール済みのファームウェアと選択したイメージを メジャー.マイナー.
  パッチ で表示します。パッチは両側が持っている場合にのみ比較に加わり、これに
  対応しない古いボード（`0x7E9` を送らない）は メジャー.マイナー のまま動作し、
  パッチはそれを通知したブートローダーに対してのみ END_UPDATE に入ります。
  イメージがボードの報告より古いか、同じか、新しいかがログに表示されます。
- **最新の GitHub リリースのファームウェア**——バイナリは git のファイルではなく、
  URTC の各バージョンのリリースに添付されたアセットです。一覧は `JuanenRac/URTC`
  のリリース API から取得し（選択したボードのアプリケーションイメージのみ、
  それぞれ `.sha256` と `.manifest.json` 付き）、ダウンロードしたイメージは
  リリースが公開するダイジェストと一致する必要があり、イメージ・マニフェスト・
  署名の確認はそのまま残ります。GitHub は CORS ヘッダーを送らないホストから
  ファイルを配信するため、ブラウザーではダウンロードできない場合があります。
  その場合はログに表示され、同梱フォルダーのイメージを使うか、リリースの
  ページからダウンロードして `.manifest.json` と一緒に「参照」で選択できます。
- **ボード設定**：拡張ボードタイプ / MLX9064x センサーバリアント /
  フリーツール構成（ID ピン `11111`）/ 周辺機器情報とシリアル番号——
  `0x1A0`-`0x1A7`。

#### SWD/JTAG ——設計上、ブラウザからは利用できません

SWD/JTAG デバッグプローブを駆動できる Web API は存在しません——Web Serial
は（USB-CAN アダプターのような）シリアルフレームデバイスとのみ通信し、
プローブ自身のプロトコルとは通信しません。STM32CubeProgrammer/pyOCD は、
デスクトップツールが呼び出すネイティブサブプロセスです。これはブラウザ
サンドボックス内で実行することの構造的な制限であり、ここに欠けている
機能ではありません。Flasher Studio の SWD/JTAG タブは、参考として、
デスクトップ版 `URTC Flasher` ツールがローカルで実行する正確なコマンドを
説明します——フルチッププログラミング、オプションバイト/RDP チェック、
または一括消去前の完全なフラッシュバックアップには、そのツールを直接
使用してください。

### Tester Studio ——実際の機能カバレッジ

`URTC-TESTER` 自身の Qt Quick デッキのパネル
(`assets/qml/TesterDeck.qml`) から移植され、同じ CAN ID に対して動作します：

- ツールごとに 1 つのパネル（電烙铁 + ワイヤーフィーダー、共有される
  単純なステッピングモーションツール、真空ピックアップ、ドリル、AOI、
  レーザー、3D プリンターのヒーター/モーション/ファン、スキャンプローブ、
  電磁石、スポット/超音波溶接機、ADS1115 の高度なパスを含むフライング
  プローブ、UV 硬化、ホットエアリワーク、圧接、サーマル検査、ペースト
  噴射）、それぞれがそのツールの実際のコマンドバイトを送信し、実際の
  テレメトリをデコードします。
- ファームウェア側の通信ウォッチドッグを持つすべてのツール（はんだごて、
  レーザー、UV 硬化、ホットエアリワーク、3D プリンターノズル——250ms
  ウォッチドッグの下で 150ms 再送信；3D プリンターレイヤーファン——
  自身の 1000ms ウォッチドッグの下で 400ms 再送信）向けの**アクティブ
  チェックボックス + キープアライブ**。再送信間隔はデスクトップツールと
  同じです。チェックを外したとき、パネルやタブを切り替えたとき、接続を
  切ったとき、ページを閉じたときに、そのツールのオフコマンドが送信されます。
- **Global Controls**（`0x100`）、**Expansion Board** の SPI パススルー
  + TMC DIAG0 照会（`0x180`-`0x183`）、**F-RAM** の照会/消去
  （`0x190`-`0x192`）、**Self-Test**（ツールごとの安全な静止状態チェック）、
  `.trc`/`.asc` トレースエクスポート付きの **Raw Bus Monitor**、そして
  任意の繰り返し間隔を持つ **Custom Frame** インジェクター——CAN Bus
  Protocol Analyzer 自身のフレームインジェクターと同様に検証されます：
  `0`-`7FF` の範囲外の識別子、無効なデータバイト、8 バイトを超えるデータは
  メッセージとともに拒否され、マスク、破棄、切り詰めは行われません。
  ボードだけが送信する識別子は拒否され、ボードのメモリへの書き込み、
  ブートローダーコマンド、アクチュエーターコマンドは事前に確認されます。
- **Detect Hardware** は実際の現在のツール（`0x110`/`0x111`）とボード
  バージョン（`0x7F8`/`0x7F9`）を照会し、宣言された重大エラー（`0x111`
  バイト 1）はライブの障害バナーとして表示されます。

- **証跡タブ。** フラッシャー、テスター、アップデーターが書き込むレコード（`urtc-evidence/1`）を、ユーザーが選んだファイルから読み込み（何もアップロードされません）、共通コードと同じ規則と同じダイジェストで一つずつ検査して新しい順に一覧にします。種類、結果、テキストでの絞り込み、要約、無効なレコードごとの問題点、CSV ダウンロードがあり、ページは 8 言語に対応しています。

- **純粋関数で組み立てるフレーム。** 各パネルのフレーム（状態 LED とリング、SPI パススルー、オプション機能、3D プリンターヘッドのノズルとエクストルーダー、溶接パルス、ステッピングモーターの動き）は `toolFrames.ts` で、ファームウェア更新のフレーム（START_UPDATE、4 つの署名チャンク、イメージのデータフレーム、END_UPDATE）は `flashFrames.ts` で組み立てられます。フィールドに収まらない値は収まる最も近い値に丸められ、テストがバイトを固定します。

- **応答付きのラック試験台。** シミュレートされたラックは、すべての命令に応答フレーム（確認応答、または理由付きの拒否）で答えます。`rackSim.ts` がそれを書き込み・読み取り（`encodeRackReply`、`parseRackReply`）、試験台パネルは理由をページの言語で伝え、早すぎて保留されたコマンドはファームウェアと同じく理由付きの拒否になります。

- **CAN トレースタブ。** 記録したトレース(`.trc` または `.asc`)を開き、仕様に従って名前を付けたフレームを一覧にします(`canTrace.ts`、パネルと同じレイアウトを使用)。拒否と障害に印が付き、短すぎる・重複した・順序が違う・長い無通信の後に来たフレームにも印が付きます。表は識別子、種類、ノード、結果、時間、テキストで絞り込め、タイムラインで拒否の位置が分かり、選択範囲は CSV または JSON で保存できます。ファイルはページ内で読み込まれ(何もアップロードされず、内容が実行されることもありません)、上限は 5 MB・200,000 フレームで、ページは 8 言語に対応しています。

### 1本のバスに複数のツールヘッド

ファームウェアは複数のツールヘッドを1本のCANバスで共有できます（マルチノード拡張）。これは**初期状態でオフ**で、ヘッドが1つのバスはこれまでとまったく同じに動作します。**ヘッド**ウィンドウはヘッドを検索し、それぞれをアドレス・ツール・シリアル番号とともに一覧し、準備完了・選択中・アドレスの競合・異常を保持・ブートローダー中・喪失のいずれかの状態を示します。1つを選ぶと確認が求められ、それからはじめてそのヘッドに何かが送信されます。バス上に複数のヘッドがある間は、1つが選択されて確認応答するまでコマンドは拒否されます。選択中のヘッドを見失うと、すべてのヘッドが安全状態になります（ウィンドウのチェックボックスでオフにできます）。バスのモデルに対してのみ試験しており、実機では未試験です。URTC-COMMON の `docs/MULTINODE.md` を参照してください。

## 🔒 セキュリティと安全

| 脅威 | 防御 |
|---|---|
| 不正なフレームが配線や画面に届く | SLCAN リンクの両方向を検証します。`0x000`-`0x7FF` の範囲外の識別子、8 バイトを超えるペイロード、`0x00`-`0xFF` の範囲外のバイトは書き込む前に拒否され、本物の SLCAN フレームではない受信行は破棄されます |
| ページに秘密が含まれる | アプリに署名キーは含まれません。Flasher Studio は URTC のビルドが各イメージの隣に公開した署名を送るだけなので、ページは公開ホスティングできます |
| 誤った、または改ざんされたファームウェアイメージ | マニフェストの `sha256` がファイルと一致しなければ書き込みはブロックされます。正式リリースの各イメージには Ed25519 のリリース署名があり、ページはイメージを送る前にブラウザー内で確認します |
| 模擬の応答を本物と取り違える | サンドボックスのタブは何も送信せず、ボードが接続されている間は何も応答しません。そのフレームには SIM、再生したトレースには REPLAY の印が付きます |
| 誤ってボードに作用する操作 | レーザー、ドリル、UV 硬化、溶接、ヒーター、動作、ペーストジェッティング、ボードのメモリへの書き込み、手入力した危険なフレーム、公開開発キーで署名されたイメージは、先に確認を求めます |
| 動き続けるアクチュエーター | ファームウェアのウォッチドッグを持つツールは再送で生かされ、パネルの交換、タブの切り替え、ボードの切断、ページを閉じたときに停止されます。STOP ALL はページが生かしているものをすべて停止します |
| 他所からコードを読み込むページ | コンテンツセキュリティポリシー：スクリプトはページ自身からのみ、接続は自身と GitHub のみ |

STOP ALL はソフトウェアのコマンドで、非常停止ではなく、上記のどの検査も安全機能ではありません。

### シミュレーターの分離と確認ダイアログ（ソフトウェアによるチェックであり、安全機能ではありません）

- サンドボックスタブ（Control、OLED、Thermal IR）は何も送信しません。そのフレームには SIM の印が付き、ボードが接続されている間はシミュレートされた応答を生成しません。プロトコルアナライザーの定義済みメッセージのうち、接続中のボードに送られるのは単純な問い合わせだけで、残りはシミュレーションのままです。
- Tester Studio は、ボード自身が報告した（`0x111`）ツールのパネルだけを表示し、ボードが応答するまでは何も表示しません。
- レーザー、ドリル、UV 硬化、溶接、ヒーター、動作、ペースト噴射、ボードのメモリへの書き込み、危険を伴う手入力フレームは、事前に確認を求めます。
- ヘッダーの **すべて停止**（接続中に表示）は、このページが動作を維持しているすべてのアクチュエーターをオフにします。ページを閉じる、接続を切るときも同じ処理が行われます。これはソフトウェアのコマンドであり、非常停止ではありません。
- 公開されている開発用の鍵で署名されたイメージを書き込む前には確認が求められます。その鍵は誰がイメージを作ったかを何も証明しないためです。
- ボードが重大なエラーを通知した場合、ボードが報告していれば、バナーに熱暴走保護の理由も表示されます。
- **記録したトレースの再生**（CAN Bus Protocol Analyzer）: Raw Bus Monitor がエクスポートしたものなどの `.trc` または `.asc` ファイルの受信フレームを、ボードなしでログとパネルに 0.25x から 10x で、必要ならループで再生します。フレームには REPLAY の印が付き、何も送信されず、記録がリクエストに応答することも、ボードの発言としてエクスポートされることもなく、ボードが接続されている間は再生が一時停止します。

### セキュリティに関する注記：このアプリに署名鍵はありません

0.2.3 以降、このアプリは HMAC-SHA256 署名鍵を**一切**含みません。URTC の
ビルドが各アプリケーションイメージを自ら署名し（リリースビルドでのみ非公開鍵を使用。公開イメージは公開の開発用鍵を使用）、署名をイメージの隣に公開します。Flasher Studio はその署名を運ぶ
だけで、デスクトップ版 `URTC Flasher` と同じ方式です。JS バンドルに秘密は
含まれないため、ページを公開ホストしても問題ありません。

唯一の例外は、マニフェストのない自作イメージをベンチ用ボードに書き込む場合
です。このときアプリは署名鍵を尋ね、その 1 回の書き込みの間だけメモリに保持
し、保存はしません。公開開発鍵で署名されたイメージ（マニフェストの
`signing_key_kind: "dev"`）は、同じ方法でビルドされたブートローダーを持つ
ボードにしかインストールできません（ログに表示されます）。URTC の
`docs/FIRMWARE_SIGNING.TXT` を参照してください。

このフォルダーは **git にありません**。`npm run sync-firmware` が作成します（CI と Pages のビルドは、テストとビルドの前にこれを実行します）。公式リリースがまだない間は、GitHub の「latest」が 404 を返すため、代わりに使うリリースを `firmware-release.json` が指定します（現在はベンチ用のプレリリース）。公式リリースが公開されたら、このファイルを削除するかタグを変更してください。**ページのセキュリティ**：スクリプト、スタイル、フォント、画像はページ自身から読み込まれ（フォントはアプリに同梱されており、フォントサーバーへのリクエストはありません）、インラインで許可されるのは React が書き込むスタイル属性だけです。ページが接続できるのは自分自身のオリジンと、リリースを配信する GitHub のホストだけです（ビルドされた `index.html` の Content-Security-Policy）。ヘッダーを送れるホストは `public/_headers` を使います（同じポリシーと `Permissions-Policy: serial=(self)`、それ以外に強力な権限はありません）。GitHub Pages はヘッダーを送れないため、そこではページ内のポリシーだけが適用されます。

`public/firmware/` には URTC が公開したファイルがそのまま（同じ名前、同じ
バイト、付属ファイル付き）入っています。URTC のバイナリは git にはなく、各
バージョンの GitHub リリースのアセットです。`npm run sync-firmware` は最新の
リリースをダウンロードし（特定のリリースは `npm run sync-firmware -- --tag v0.3.5`）、
またはローカルフォルダーを引数に取ります（ベンチビルドは
`npm run sync-firmware -- ../URTC/firmware`）。どちらの場合も `public/firmware/`
に触れる前に各ダイジェストと署名フィールドを確認し、
`src/lib/bundledFirmware.ts` を再生成します。テストがマニフェストと照合して
検証します。

公式リリースの各ファイルにはリリース署名（`<ファイル>.sig`、Ed25519）があります。同期は署名がある場合に検証し、不正な署名は拒否します。署名のないセット（ベンチ用プレリリースやローカルビルド）には `--allow-unsigned` が必要です。 ページはバンドル済みイメージまたは GitHub リリースのイメージをボードへ送る前に、同じ署名をブラウザ（Web Crypto）で検証し、無効なら中止します。

## 🔌 インターフェース

- **SLCAN** ファームウェアを実行する USB-CAN アダプター（例：
  `candlelight`/`slcan` を実行する CANable、または標準的な `lawicel`
  SLCAN シリアルプロトコルを話す任意のアダプター）——2 つのデスクトップ
  ツールがそれぞれの Serial トランスポート経由でサポートしているのと
  同じアダプタークラスです。
- バスは **500 kbit/s** に設定してください。接続時に、アプリは 500、250、125 kbit/s などの標準レートを順に試し、ボードがバージョン問い合わせに応答した最初のレートを使用します。レートを手動で選ぶことや、ボードの応答なしに受信だけを行うことはまだできません。
- Web Serial をサポートするブラウザ——**Chrome または Edge**。Firefox
  と Safari は Web Serial を実装しておらず、まったく接続できません。
- Web Serial にはセキュアコンテキスト（HTTPS）または `localhost` のいず
  れかが必要であり、iframe の内部からは使用できません。本アプリを埋め
  込みフレーム内でプレビューしている場合は、まず自身のタブで開いて
  ください。

### CAN フレーム検証

SLCAN リンクは両方向とも、UI や回線に届く前に検証されます
（`src/hooks/useSerialCanBus.ts`）：

- **送信** - `sendFrame()` は、ID が 11 ビットの標準 CAN 範囲
  （`0x000`-`0x7FF`）を外れている場合、ペイロードが 8 バイトを超える
  場合、またはペイロードのいずれかのバイトが `0x00`-`0xFF` を外れている
  場合にコマンドのシリアライズを拒否します。UI は無効なテキストを
  シリアルポートに書き込む代わりに「Refusing malformed CAN frame: ...」と
  表示します。
- **受信** - `processBuffer()` は、受信した SLCAN 行を `CanFrame` に
  変換する前に、実際の `t<3桁 16進数 ID><1桁 16進数 DLC 0-8><16進数ペイロード>`
  との一致を要求します；DLC が `0`-`8` の範囲外だったり、ペイロードが
  自身の宣言長より短い場合は、ツールパネルに `NaN` バイトとして
  渡す代わりに、コンソールに警告を記録して破棄します。末尾のオプションの
  アダプタタイムスタンプは、有効なペイロードの後に引き続き受け入れられます。

## 🚀 クイックスタート

### 前提条件

- Node.js 20 LTS+
- npm

### インストール

```bash
git clone https://github.com/JuanenRac/URTC-WEB-STUDIO.git
cd URTC-WEB-STUDIO
npm install
```

### 開発モード

Vite の開発サーバーでライブリロード付きでアプリを実行します：
- **Windows：** `dev.bat` をダブルクリックするか、`npm run dev` を実行
- **Linux/Mac：** `./dev.sh` または `npm run dev` を実行

その後、Chrome または Edge で `http://localhost:3000` を開いてください。

開発サーバーは `localhost` でのみ待ち受けます。Web Serial は https または localhost で動作するため、ネットワークに公開しても意味がありません。

### 静的ビルド

`dist/` 内に静的な、最適化されたバンドルへコンパイルします：
- **Windows：** `build.bat` をダブルクリックするか、`npm run build` を実行
- **Linux/Mac：** `./build.sh` または `npm run build` を実行

これは純粋な静的サイトです——（`HYDRA-UMC STUDIO` 自身の `server.ts` とは
異なり）バンドルされたサーバーコンポーネントはありません。ビルドされた
`dist/` フォルダをローカルでプレビューするには：

```bash
npm run preview
```

または、お好みの静的ファイルホストで `dist/` を配信してください。
`npm run lint` は TypeScript コンパイラをチェックのみモードで実行します。

ビルドされたページはコンテンツセキュリティポリシー（スクリプトはページ自身からのみ、接続はページ自身と GitHub のみ）を宣言し、各タブを初めて開いたときに読み込みます。`npm run test:e2e` が実際の Chromium でモデル化したボードに対して動かしますが、実際のアダプターではまだ試していません。

### GitHub Pages（所有者が有効にするまで停止）

## 🗺️ ロードマップと既知の制限

- 受信専用モードとビットレートの手動選択：どのボードも応答しないバスには接続できません。

- ブラウザー内で GitHub リリースからファームウェアファイルを直接ダウンロードすること：GitHub は CORS ヘッダーのないホストからリリースのファイルを配信するため、ダウンロードがブロックされることがあります（同梱イメージ、またはディスクから `.manifest.json` と一緒に選んだファイルは常に使えます）。

**ブラックボックス、オプション機能、ラック試験台、熱画像のタブ(新規、模擬部品での確認のみ):** Tester Studio は障害レコーダー(`0x1A8` / `0x1A9`)を読み、CSV または JSON でダウンロードします。オプションがオンなら、ボードがエラーを報告するたびに一度だけ自動で読みます。ファームウェアのオプション機能(`0x1AE` / `0x1AF`、既定でオフ、確認の後に切り替え、次の電源投入後に有効)を切り替えられます。ヘッドごとの識別(種類とシリアル番号)を備えたツールラックをページ内で模擬し、熱検査画像を疑似カラーで描画します(模擬画像はその旨を表示)。ツールカタログは URTC-COMMON 共通のツールプロファイルから取得するようになりました。実機では試していません。

**ブラックボックスビューア（新規、テストでのみ確認）:** Black Box タブは、エラー前に記録された数秒間の測定温度と設定値を描画し、エラーフラグが最初に現れる位置に線を引きます。ボードを接続しなくても、以前に保存した記録（このタブ自身が書き出す JSON または CSV ファイル）を開けます。記録ではないファイル、範囲外の値があるファイル、67 サンプルを超えるファイルは理由付きで拒否されます。

**オフラインコピーとインストール（新規、テストとブラウザーでのみ確認）:** ビルドはサービスワーカー（`sw.js`）と Web アプリマニフェストを書き出します。https（または localhost）での初回アクセス後、ブラウザーはページ、そのスクリプト、同梱のファームウェアを保存し、ヘッダーに **オフライン対応** と表示され、Studio はネットワークなしで開きます（そのときヘッダーには **オフライン** と表示されます）。ブラウザーが対応していれば、**インストール** ボタンで Studio をアプリとしてインストールできます。ページとファームウェアのマニフェストは常に先にネットワークへ要求するため、オンラインなら最新のものが得られます。`version.json` は保存コピーから返されることはありません。新しいバージョンは、開いているタブが閉じられるまで引き継ぎを待ちます。GitHub API は保存されません。ネットワークがないと最新リリースを調べられず、同梱のイメージだけが使われます。

**熱カウンタの経時変化（新規、テストとモデル化したボードでのみ確認）:** ブラックボックスタブでは、累計の熱カウンタ（`0x1AA` / `0x1AB`）を 10 秒、30 秒、1 分、5 分ごとに読み直せます。各読み取りはブラウザーに保存される履歴に追加され、ヒーターの時間と異常の推移をグラフにし、CSV としてダウンロードや消去ができます。カウンタが減った場合（別のボード）は履歴を最初からやり直します。

**保存したセッション（新規、テストとモデル化したボードでのみ確認）:** バスモニターはフレームをログと、ログを SHA-256 とサイズで特定するレコードとして保存します。形式はデスクトップ版テスターと同じです。**保存したセッションを検証** はレコードとそのログを受け取り、対応しているかを伝えます。ログが編集されていないことを示します。ブラウザーが Ed25519 署名を作れる場合、レコードにはこのブラウザーの鍵（初回使用時に作成され、ブラウザーに保存されます）による署名も付きます。署名はレコードが署名後に編集されていないことを示しますが、鍵の持ち主が誰かは示しません。 モニターは、入力した ID のみ、またはデータが変わったフレームのみを表示することもできます（レートと負荷は引き続きすべてのフレームを数えます）。

**バージョン通知（新規、テストでのみ確認）:** ビルドはページの隣に `version.json` を書き出します。ビルド済みのページは、開いたときに一度だけ、同一オリジンに限って自分のバージョンと比較し、より高いバージョンが配信されていれば「再読み込み」ボタン付きで知らせます。自動では再読み込みせず、同じか古いバージョンでは何も表示せず、ファイルがない場合やネットワークがない場合も何も表示しません。

**ヒーターの PID（「オプション機能」タブ内。新規、模擬でのみ確認）:** Tester Studio はファームウェアのヒーター PID の状態（`0x1B9` / `0x1BA`: 有効なゲイン、状態、直前の制御周期の出力）を読み、ゲイン（0〜600）を保存し、リレー式オートチューニングを開始または中止します。オートチューニングは、はんだごての現在の設定温度（100〜445 C）付近でコテ先を加熱し、見つかったゲインを保存します。ゲインの保存とオートチューニングの開始には確認があり、中止にはありません。0〜600 の数値でないゲインは何も送る前に拒否されます。先にオプション機能でこの機能をオンにする必要があります。実際の基板では試していません。
